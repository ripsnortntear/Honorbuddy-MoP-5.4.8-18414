# Honorbuddy MoP 5.4.8 (Build 18414) Codebase Analysis

## Executive Summary
This workspace is a complete distribution and development tree for **Honorbuddy MoP 5.4.8 (18414)**, a .NET-based game automation platform for World of Warcraft: Mists of Pandaria (32-bit x86 DirectX 11).

> [!IMPORTANT]
> **.NET 4.5.1 / C# 5.0 Strict Compatibility Requirement**
> All code in this repository dynamically compiled by Honorbuddy at startup (or built against its assemblies) must strictly comply with **.NET Framework 4.5.1** (C# 5.0).
> - **Forbidden (C# 6.0+)**:
>   - Interpolated strings (`$"Hello {name}"` $\rightarrow$ use `string.Format("Hello {0}", name)`)
>   - Null-conditional operators (`obj?.Method()` $\rightarrow$ use `if (obj != null) obj.Method()`)
>   - Expression-bodied members (`int Prop => 5;` $\rightarrow$ use full getter blocks)
>   - Auto-property initializers (`public int Val { get; set; } = 10;`)
>   - `nameof(...)` operator (`nameof(variable)` $\rightarrow$ use `"variable"`)
>   - Inline out declarations (`out var x` $\rightarrow$ declare `Type x; ... out x`)
>   - Pattern matching, tuples `(a, b)`, and local functions.

### 1. Core Executables & Native Hooks
* **Honorbuddy.exe** (`2.5.11489.748`): 32-bit x86 .NET 4.5.1 executable. Contains core bot logic, the `Styx` framework, `Styx.TreeSharp` behavior trees, object manager reflection, and the plugin/routine assembly loader.
* **GreyMagic.dll**: External memory read/write engine that attaches to 32-bit `Wow.exe`.
* **SlimDX.dll**: Managed DirectX 11/9 wrapper for game rendering hooks and GUI overlays.
* **RemoteASM.dll / RemoteASMNative.dll**: FASM wrapper for dynamic assembly injection into the WoW process.
* **Tripper.RecastManaged.dll / Tripper.Tools.dll**: Detour/Recast navmesh pathfinding engine.

### 2. Bots (`Bots/`)
Each bot derives from `Styx.CommonBot.BotBase`:
* **AutoAngler2**: Automated fishing bot with smart lure application, pool navigation, and gear switching.
* **Professionbuddy**: Behavior-tree-driven trade skill, crafting, and farming engine.
* **Tyrael / LazyRaider / Templar / Combat**: Raiding and movement assist bots where player controls positioning while routine handles combat.

### 3. Combat Routines (`Routines/`)
Each routine implements `Styx.CommonBot.Routines.ICombatRoutine`:
* **Demonic** (Warlock, by Millz)
* **GladiatorSuite** (DK, Hunter, Mage, Priest, Warlock, Warrior)
* **Singular** (Official all-class routine v3.0.0.3502)
* **TuanHA** (Special Editions for DK, Hunter, Monk, Paladin, Rogue, Shaman, Warrior)
* **PureRotation**, **Fury Unleashed**, **Leaves**, **Oracle**, **vitalicrotation**, etc.

### 4. Plugins (`Plugins/`)
Over 50 plugins implementing `Styx.Plugins.HBPlugin`:
* `KBA` (Keep Buff Active), `ItemForAuraQuestHelper`, `ObjectGatherer`, `Pandaria Dailies v2`, `BattlePetSwapper`, `Zaprecorder2`, `Pokehbuddy`, `Milling`, `prospecting`, etc.

### 7. Runtime `ExpressionSet.Compile` Crash Investigation & Resolution - Completed
* **Incident Description**:
  - During live testing of [`[A - Quest] EK 12-58 [Kick].xml`](file:///D:/Games/GH%20of%20HB/Default%20Profiles/1-90%20Questing%20Profile%20Pack/Classic/%5BA%20-%20Quest%5D%201-58%20%5BKick%5D/%5BA%20-%20Quest%5D%20EK%2012-58%20%5BKick%5D.xml), the bot stopped abruptly at line 3777 with:
    ```
    Compiling expression '!IsQuestCompleted(26761)' @ line 3777
    Unable to evaluate/compile condition in If tag. Please check your profile.
    Honorbuddy stopped
    System.ArgumentOutOfRangeException: Index was out of range. Must be non-negative and less than the size of the collection.
    Parameter name: index
       at Styx.CommonBot.Profiles.Quest.Order.ExpressionSet.Compile(ExpressionError[]& errors)
       at Styx.CommonBot.Profiles.Quest.Order.ConditionHelper.Class716.smethod_0(String string_1, Nullable`1 nullable_1)
       at Styx.CommonBot.Profiles.Quest.Order.ConditionHelper.Class716.method_0()
       at Bots.Quest.QuestOrder.ForcedIf.OnStart()
    ```
* **Root Cause Reverse Engineering**:
  1. **Condition Evaluation Architecture**:
     - Honorbuddy contains a fast-path regex evaluator (`Class601`) that matches 6 specific composite patterns (`HasQuest && IsQuestCompleted`, `HasQuest && !IsQuestCompleted`, `!HasQuest && IsQuestCompleted`, `!HasQuest && !IsQuestCompleted`, `HasQuest`, and `!HasQuest`).
     - Condition expressions outside these 6 patterns (such as `!IsQuestCompleted(26761)`) return `null` from `Class601.smethod_0`, forcing the engine to compile a dynamic lambda via `ExpressionSet.Compile`.
  2. **The AppDomain Assembly Reference Leak**:
     - Inside `ExpressionSet.Compile`, Honorbuddy enumerates all loaded assemblies in the AppDomain:
       ```csharp
       foreach (var asm in AppDomain.CurrentDomain.GetAssemblies())
           if (!asm.IsDynamic && !string.IsNullOrEmpty(asm.Location))
               cp.ReferencedAssemblies.Add(asm.Location);
       ```
     - Prior builds of `Bots/AutoAngler2/AutoAngler2.csproj` lacked `<Private>False</Private>` on references to `Honorbuddy`, `Tripper.Tools`, and transitive assemblies.

### 17. ProfessionBuddy Deep Dive & Stability Overhaul
* **Overview & Role**:
  - `ProfessionBuddy` ([`Bots/Professionbuddy`](file:///D:/Games/GH%20of%20HB/Bots/Professionbuddy)) is an advanced botbase designed for profession leveling, automated crafting, auction house management, mail processing, bank operations, and multi-bot orchestration.
  - Authored by HighVoltz, it contains its own visual action/composite tree editor, XML serializer, coroutine-based execution tree, and a dynamic C# code compiler.
* **Why ProfessionBuddy Failed to Load in Honorbuddy**:
  - During Honorbuddy startup, `AssemblyLoader<BotBase>` scans all subfolders in `Bots/` and uses Roslyn / C# CodeDOM to compile each botbase into a temporary assembly, then instantiates classes extending `BotBase` via `Activator.CreateInstance`.
  - While other external botbases (`AutoAngler2`, `LazyRaider`, `Tyrael`, etc.) loaded successfully, `ProfessionBuddy` silently failed without a compilation error.
  - **Root Cause**: `ProfessionbuddyBot` declared a static field:
    ```csharp
    public static readonly string BotPath = GetProfessionbuddyPath();
    ```
    This field was initialized during the class static constructor (`.cctor()`) before any instance was created.
    Inside `GetProfessionbuddyPath()`:
    1. `GlobalSettings.Instance.BotsPath` was accessed directly. During bot scanning at startup, `GlobalSettings.Instance` is not yet initialized (`null`), triggering an immediate `NullReferenceException`.
    2. The method called `asmName.Substring(0, asmName.LastIndexOf("_"))`. When compiled dynamically without an underscore in the assembly name, `LastIndexOf` returned `-1`, throwing `ArgumentOutOfRangeException: Length cannot be less than zero`.
    3. The resulting `TypeInitializationException` caused `TypeLoader<BotBase>` to catch an unhandled exception and drop `ProfessionBuddy` from the loaded bot list.
* **Key Architectural Discoveries**:
  1. **Dual-Bot Execution Model**:
     - `ProfessionbuddyBot.Root` is a coroutine action:
       ```csharp
       new ActionRunCoroutine(async ctx => await Branch || await ExecuteSecondaryBot())
       ```
     - When the active PB profile composite tree returns `false` (e.g. while waiting for auctions, materials, or intermediate steps), execution seamlessly delegates to `SecondaryBot` (such as Gatherbuddy2, Questing, or Grind Bot). This enables uninterrupted farming and grinding between crafting cycles.
  2. **Dynamic C# Code Compilation (`DynamicCodeCompiler`)**:
     - PB allows profile authors to write embedded C# code expressions (conditions, coroutine actions, variable manipulators `var1`..`var9`, custom methods).
     - At profile load time, `DynamicCodeCompiler` generates a runtime `CodeDriver` class wrapping user expressions and compiles it using `CSharpCodeProvider`.
     - *Bug Found & Fixed*: `_usingHBLite` dereferenced `Assembly.GetEntryAssembly().GetType(...)` without checking if `GetEntryAssembly()` was null. Additionally, `options.ReferencedAssemblies` looped over `AppDomain.CurrentDomain.GetAssemblies()` without validating `asm.Location`, causing empty strings and duplicate assembly paths to be passed to `csc.exe`.
  3. **DataStore Addon Integration**:
     - PB reads Lua saved variables from the `DataStore` WoW addon family (`DataStore_ContainersDB`, `DataStore_CraftsDB`, etc.).
     - This allows PB to check items across bank, guild bank, bags, and alt characters on the same account without requiring manual character swapping.
  4. **Direct Process Memory Reads in Tradeskill**:
     - `Tradeskill.HasSpell(uint spellId)` read WoW process memory directly using `GlobalPBSettings.Instance.KnownSpellsPtr`.
     - *Bug Found & Fixed*: If offsets changed, pointers were zero, or `GlobalPBSettings` was null, memory access crashed. Hardened with pointer validation, `try/catch`, and graceful fallback to `Styx.CommonBot.SpellManager.HasSpell((int)spellId)`.
  5. **Empty Stub Folders**:
     - The directories `Bots/Professionbuddy/Actions/` and `Bots/Professionbuddy/Composites/` contain 37 files containing only `// Scheduled for deletion`. The active components were previously migrated to `Components/` and `ComponentBase/`.
* **Fixes Applied & Committed**:
  1. **`ProfessionBuddy.cs`**: Robust path resolution with fallback chain (`GlobalSettings` -> `Utilities.AssemblyDirectory` -> `AppDomain.CurrentDomain.BaseDirectory` -> `Bots/Professionbuddy`).
  2. **`Tradeskill.cs`**: Safe memory pointer reading with automatic fallback to `SpellManager.HasSpell`.
  3. **`Dynamic/DynamicCodeCompiler.cs`**: Null guards for `GetEntryAssembly()` and sanitized assembly references avoiding `csc.exe` duplicate argument failures.
  4. **`ProfessionBuddy.csproj` & `BehaviorTree.csproj`**: Fixed invalid HintPaths (`..\..\Honorbuddy.exe`, `..\..\GreyMagic.dll`, `..\..\Tripper.Tools.dll`).
  - **Assembly Reference De-Duplication (`SafeAddReference`) & CS1703 Prevention**:
    - *Vulnerability Discovered*: During dynamic quest behavior compilation (`QuestBehaviorHelper.GetBehaviorInstanceType`) or runtime profile loading, `CodeCompiler..ctor` iterated `AppDomain.CurrentDomain.GetAssemblies()` which already contained `System.Runtime.Caching` (e.g. `C:\Windows\...\System.Runtime.Caching.dll`). When `CodeCompiler` subsequently called `AddReference("System.Runtime.Caching.dll")`, the legacy `StringCollection.Contains` check failed because the exact string differed from the GAC full path, appending both paths to `CompilerParameters.ReferencedAssemblies`. `csc.exe` then failed with fatal compiler error `CS1703: An assembly with the same identity 'System.Runtime.Caching...' has already been imported`.
    - *Remediation*: Implemented `AssemblyCacheHelper.SafeAddReference(CompilerParameters options, string assembly)` and replaced `CodeCompiler.AddReference` body to route through it. `SafeAddReference` de-duplicates assembly references case-insensitively using `Path.GetFileNameWithoutExtension`. Duplicate entries (regardless of whether specified as simple names or fully qualified paths) are silently ignored.
    - *Result*: `Quest Behaviors` now compiles with 0 errors and generates deterministic binary [`CompiledAssemblies\Quest Behaviors_A997E3A3.dll`](file:///D:/Games/GH%20of%20HB/CompiledAssemblies/Quest%20Behaviors_A997E3A3.dll), which loads instantaneously on all subsequent profile loads without invoking `csc.exe`.
* **Verification & Validation**:
  - Full MSBuild build (`MSBuild.exe ProfessionBuddy.csproj /t:Build /p:Configuration=Release`) passes with **0 Errors**.
  - Reflection instantiation test (`Activator.CreateInstance`) in 32-bit CLR confirms `HighVoltz.Professionbuddy.ProfessionbuddyBot` successfully initializes with `Name = "ProfessionBuddy"`, `PulseFlags = All`, and `RequiresProfile = False`.
  - Committed and pushed to `oldsmarchaos/main` (`c7348e6e`).

### 20. Singular Combat Routine Performance & Decision-Making Overhaul
* **Objective**: Overhaul the default open-source **Singular** combat routine ([`Routines/Singular`](file:///D:/Games/GH%20of%20HB/Routines/Singular)) across speed, frame efficiency, and combat decision making so it rivals premium routines (Demonic, GladiatorSuite, Insanity, TuanHA).
* **Root-Cause Analysis & Bottlenecks Identified**:
  1. **Latency Traps in `Spell.Cast`**:
     - `Spell.cs` wrapped cast execution in a blocking `WaitContinue(TimeSpan.FromMilliseconds(350), ret => ...)` where instant-cast spells (`cctx.spell.CastTime == 0`) failed `Spell.GcdTimeLeft.TotalMilliseconds > 750` and were forced to stall the entire behavior tree thread for the full 350ms timeout on every cast!

  2. **High CPU Allocations per Behavior Tree Tick**:
     - `Unit.NearbyFriendlyPlayers` and `Unit.NearbyUnfriendlyUnits` performed full, unthrottled iterations of `ObjectManager.ObjectList` and `GetObjectsOfType<WoWPlayer>` on every property call. In rotation logic checking party/enemy counts, this caused 5–15 full object manager scans and list allocations per behavior tree pulse (10–30 Hz).
     - Redundant duplicate calls to `CanCastHackIsCastInProgress` in `Spell.CanCastHack`.
  3. **Combat Decision-Making Deficiencies**:
     - Lack of total damage immunity checks: offensive single-target and AoE rotations would repeatedly waste spells, cooldowns, and resources attacking players inside Divine Shield, Ice Block, Cyclone, Deterrence, or Banish.
     - Slow, delayed interrupts: `CreateInterruptBehavior` was throttled to 500ms intervals and required at least 250ms cast time remaining, causing fast-cast kicks and counterspells to miss frequently.

## 27. Questing Loot vs Harvest Oscillation Bug & Plugin POI Conflict Resolution

### 27.1 Incident Summary & Symptoms
During automated questing (e.g. running the 1–58 Eastern Kingdoms leveling profile), the bot was observed endlessly pacing back and forth between a dead mob (e.g., Bandit) and a gatherable node (e.g., Silverleaf) without completing either action. The character would arrive at the herb, begin to interact/cast, immediately abort the cast to turn toward the corpse, stop before finishing loot, turn back toward the herb, and repeat indefinitely.

### 27.2 Root Cause Analysis
Diagnostic analysis of session logs and bot execution trees identified two intersecting flaws across the plugin ecosystem and the core bot engine:

1. **Third-Party Plugin POI & Navigation Hijacking (`Plugins\RaresAndChests`)**:
   - In WoW 5.4.8, gatherable nodes (herbs and mineral deposits) share the game object taxonomy type `WoWGameObjectType.Chest`.
   - `RaresAndChests\Main.cs` queried `ObjectManager.GetObjectsOfType<WoWGameObject>().Where(c => c.SubType == WoWGameObjectType.Chest)`. Because it lacked `!c.IsHerb && !c.IsMineral` exclusions, herbs like Silverleaf were misidentified as treasure chests.
   - The plugin forced `BotPoi.Current = new BotPoi(chestItem, PoiType.Loot)` (forcing `PoiType.Loot` instead of `PoiType.Harvest`).
   - Simultaneously, `CombatLooter` in `HBPlugin.Pulse()` observed `Lootables.Count() > 0 && !StyxWoW.Me.IsMoving`. As soon as the character stopped to interact with the herb, `CombatLooter` invoked `Navigator.MoveTo(lootTarget.Location)` (`"Moving to loot Bandit."`) directly inside `Pulse()`.
   - This raw navigation call in `Pulse()` ran outside the TreeSharp behavior tree pipeline, causing movement that instantly cancelled the herb gathering spell cast (`SPELL_CAST_FAILED Herb Gathering failure: 'Can't do that while moving'`).

2. **Core Behavior Tree Blacklist Flag Mismatch (`Bots.Grind.LevelBot.smethod_62` in `Honorbuddy.exe`)**:
   - In Questing and LevelBot routines, when an interaction times out (e.g. waiting for `LOOT_OPENED` or cast completion after movement cancellation), the timeout handler invokes `Blacklist.Add(BotPoi.Current.Guid, BlacklistFlags.Loot, ...)` to temporarily ignore unreachable targets.
   - In `LevelBot.smethod_62`, the timeout handler executed `ldc.i4.2` (`BlacklistFlags.Loot` only).
   - However, `LevelbotIncludeLootsFilter` evaluates game objects (chests and nodes) using `BlacklistFlags.Node` (flag integer 4).
   - Because `(BlacklistFlags.Loot & BlacklistFlags.Node) == 0`, the herb node was **never added to the node blacklist**. On the very next bot tick, the harvest behavior tree saw the herb as valid and re-targeted it immediately, restarting the loop.

3. **Autonomous Looter Plugins (`Combat Looter` and `NoCombat Looter`)**:
   - Both plugins previously executed loot scans and target acquisition even if `BotPoi.Current.Type != PoiType.None`, creating race conditions when the botbase was actively engaged with a quest object or node.

### 27.3 Remediation & Hardening Applied

1. **`Plugins\RaresAndChests\Main.cs`**:
   - Gated all pulse routines with `BotPoi.Current.Type == PoiType.None` and `!StyxWoW.Me.IsCasting && !StyxWoW.Me.IsChanneling`.
   - Added explicit filters `!c.IsHerb && !c.IsMineral` to chest queries.
   - Corrected chest POI assignment to `PoiType.Harvest`.
   - Rerouted `CombatLooter` to set `BotPoi.Current = new BotPoi(lootTarget, PoiType.Loot)` rather than calling raw `Navigator.MoveTo` in `Pulse()`.
   - Defaulted `CombatLooter` to `false` in settings to avoid redundant looting when Questing botbase's native loot tree is active.

2. **`Plugins\Combat Looter\Combat Looter.cs` & `Plugins\NoCombat Looter\NoCombat Looter.cs`**:
   - Added active POI guards:
     ```csharp
     if (Styx.CommonBot.POI.BotPoi.Current.Type != Styx.CommonBot.POI.PoiType.None)
         return;
     ```
   - Prevents plugins from interrupting existing botbase POIs, quest interactions, or casts.

3. **Core Engine Patch (`Honorbuddy.exe` `Bots.Grind.LevelBot.smethod_62`)**:
   - Patched IL instruction `IL_0074: ldc.i4.2` (`BlacklistFlags.Loot`) -> `ldc.i4.6` (`BlacklistFlags.Loot | BlacklistFlags.Node`).
   - If a harvest or loot attempt is interrupted or fails to open loot, both unit loot and node blacklist flags are asserted. The node is properly suppressed from subsequent pulses, allowing the bot to proceed cleanly without oscillation.
   - Validated JIT compilation across 32-bit CLR with 0 errors.

## 28. Condition Evaluation & ExpressionSet Robustness

### 28.1 Failure Mode & Symptoms
During questing profile execution (e.g., following the turn-in of quest 26152 in Elwynn Forest / Goldshire), the bot abruptly halted with:
```text
Compiling expression 'HasItem(1307)' @ line 520
Unable to evaluate/compile condition in If tag. Please check your profile.
Honorbuddy stopped
Bot stopping! Reason: Unable to evaluate/compile condition in If tag. Please check your profile.
```

### 28.2 Root Cause Analysis

1. **Missing Fast Condition Evaluators (`Class601.smethod_0`)**:
   - Bossland provided an internal regex-based fast evaluation mechanism (`Class601.smethod_0`) to evaluate simple condition strings without invoking the Roslyn/CodeDom compiler (`csc.exe`).
   - In stock builds, `Class601` only registered 6 patterns, limited exclusively to `HasQuest(uint)` and `IsQuestCompleted(uint, uint)`.
   - Very common profile tags such as `<If Condition="HasItem(1307)">`, `<If Condition="!HasItem(1307)">`, `<If Condition="(HasItem(1307))">`, and `IsQuestCompleted(uint)` alone were absent.
   - Because `Class601.smethod_0` returned `null`, condition evaluation fell through to `ExpressionSet.Compile`.

2. **Assembly Duplication (`CS1703`) in `ExpressionSet.Compile`**:
   - `ExpressionSet.Compile` enumerated `AppDomain.CurrentDomain.GetAssemblies()` and blindly added raw assembly paths into `CompilerParameters.ReferencedAssemblies`.
   - This triggered `CS1703` compiler warnings/errors (`An assembly with the same identity 'System.Runtime.Caching' has already been imported`).

3. **Unhandled `ArgumentOutOfRangeException` in `ExpressionSet` Error Mapping**:
   - When `csc.exe` produced a global or assembly-level diagnostic at `Line == 0`, `ExpressionSet.Compile` executed:
     ```csharp
     while (num >= 0 && compilerError.Line <= list[num].LineStart)
     {
         num--;
     }
     errors[j] = new ExpressionError(list[num].Expression, compilerError.ErrorText);
     ```
   - Because `list[0].LineStart` was greater than or equal to 0, `num` decremented from `0` to `-1`.
   - Indexing `list[-1]` threw an unhandled `System.ArgumentOutOfRangeException`, crashing out of `ConditionHelper.Class716.smethod_0` and breaking the Questing botbase's `ForcedIf` state tree.

### 28.3 Implementation & Remediation

1. **Native Fast-Path Condition Evaluators in `Honorbuddy.exe` (`ns35.Class601`)**:
   - Added direct static methods in `Class601` dispatching directly to `ProfileHelperFunctionsBase`:
     - `smethod_hasitem(int)` -> `profileHelperFunctionsBase_0.HasItem(int)`
     - `smethod_nothasitem(int)` -> `!profileHelperFunctionsBase_0.HasItem(int)`
     - `smethod_isquestcompleted(uint)` -> `profileHelperFunctionsBase_0.IsQuestCompleted(uint)`
     - `smethod_notisquestcompleted(uint)` -> `!profileHelperFunctionsBase_0.IsQuestCompleted(uint)`
     - `smethod_hq_hi(uint, int)` -> `profileHelperFunctionsBase_0.HasQuest(uint) && profileHelperFunctionsBase_0.HasItem(int)`
     - `smethod_hq_nothi(uint, int)` -> `profileHelperFunctionsBase_0.HasQuest(uint) && !profileHelperFunctionsBase_0.HasItem(int)`
     - `smethod_fallback_false()` -> `false`
   - Injected pattern registrations into `Class601..cctor` supporting optional enclosing parentheses and whitespace trimming:
     - `^\s*\(?\s*HasItem\s*\(\s*(?<Arg1>\d+)\s*\)\s*\)?\s*$`
     - `^\s*\(?\s*!HasItem\s*\(\s*(?<Arg1>\d+)\s*\)\s*\)?\s*$`
     - `^\s*\(?\s*IsQuestCompleted\s*\(\s*(?<Arg1>\d+)\s*\)\s*\)?\s*$`
     - `^\s*\(?\s*!IsQuestCompleted\s*\(\s*(?<Arg1>\d+)\s*\)\s*\)?\s*$`
     - `^\s*\(?\s*HasQuest\s*\(\s*(?<Arg1>\d+)\s*\)\s*&&\s*HasItem\s*\(\s*(?<Arg2>\d+)\s*\)\s*\)?\s*$`
     - `^\s*\(?\s*HasQuest\s*\(\s*(?<Arg1>\d+)\s*\)\s*&&\s*!HasItem\s*\(\s*(?<Arg2>\d+)\s*\)\s*\)?\s*$`

2. **Compilation Fallback Guard (`ConditionHelper.Class716.smethod_0`)**:
   - Patched `smethod_0` so that if compilation of dynamic expressions ever fails, it defaults to `smethod_fallback_false` (`() => false`) rather than returning `null`. This prevents faulty profile XML conditions from terminating the bot.

3. **Safe Reference Loading in `ExpressionSet.Compile`**:
   - Redirected `CompilerParameters.ReferencedAssemblies.Add` to call `AssemblyCacheHelper.SafeAddReference(CompilerParameters, string)` to eliminate duplicate assembly imports (`CS1703`).

4. **Error Indexing Bounds Protection**:
   - Clamped the mapped index `num = Math.Max(0, num)` before indexing `list[num]`, guaranteeing `ArgumentOutOfRangeException` cannot be thrown.

5. **CLR Verification**:
   - Compiled and executed a dedicated x86 test harness under the 32-bit .NET 4.5.1 runtime.
   - Pre-JIT compiled all patched methods using `RuntimeHelpers.PrepareMethod`: 100% success.
   - Verified that expressions like `HasItem(1307)`, `!HasItem(1307)`, `(HasItem(1307))`, `IsQuestCompleted(26152)`, etc., evaluate immediately into native delegates with 0 compilation latency.

## 30. Movement & Transport Subsystem Overhaul (Orgrimmar Elevators, CTM Jitter Elimination, Flightor Smoothness)

### 30.1 Problem Statement
- **Elevator Traversal Failures (Orgrimmar & WMO Transports)**: When navigating vertical terrain requiring elevators (notably Orgrimmar's central elevators connecting the Valley of Strength with the upper mesa and zeppelin towers, as well as Thunder Bluff and Undercity lifts), Honorbuddy would abort navigation, logging `"There is no elevator around. Something is wrong"` and failing movement.
- **In-Game Movement Jitter & Robotic Twitches**: Ground movement exhibited persistent micro-stuttering, rapid character shoulder twitches, and heading oscillation while traversing normal waypoints.
- **Flightor Frame Lag & Thread Freezes**: 3D aerial navigation via Flightor suffered from 50% dropped update frames and synchronous thread sleeps that caused visible stuttering during flight.
- **Transport Docking Abandonment**: In `Quest Behaviors\UseTransport.cs`, zeppelin and boat boarding frequently timed out or stranded the character on board indefinitely due to microscopic distance tolerance thresholds.

---

### 30.2 Root Cause Analysis

#### 1. Orgrimmar Elevators Ignored by `MeshNavigator`
- Honorbuddy's `MeshNavigator.smethod_8` (the elevator GameObject filter predicate) strictly checked:
  ```cil
  callvirt WoWGameObjectType WoWGameObject::get_SubType()
  ldc.i4.s 11 // WoWGameObjectType.Transport
  bne.un.s IL_0028 // Return false
  ```
- In World of Warcraft (Cataclysm 4.3.4 and Mists of Pandaria 5.4.8), Orgrimmar's central elevators are categorized by the game engine as `WoWGameObjectType.MapObjectTransport` (enum value `15`), *not* `Transport` (`11`).
- Because `smethod_8` returned `false` for subtype `15`, `MeshNavigator.method_10` never located the elevator GameObject (`woWGameObject == null`), failed elevator traversal, and returned `MoveResult.Failed`.
- Furthermore, in `MeshNavigator.method_10`, the vertical Z arrival tolerance (`Math.Abs(currentZ - elevatorZ) <= 2.0f`) was too restrictive for Cataclysm/MoP WMO elevator models where the platform visual surface is ~2.5 to 3.5 yards above the GameObject origin point.

#### 2. Ground Movement Jitter & CTM Packet Flooding
- In `Styx.WoWInternals.WoWMovement.ClickToMove(WoWPoint)`:
  ```cil
  call Styx.WoWPoint::DistanceSqr(Styx.WoWPoint)
  conv.r8
  ldc.r8 0.05 // 0.22 yards
  bgt.un.s IL_0036 // Re-issue ClickToMoveType.Move
  ```
- `MeshNavigator.method_15` runs on a high-frequency pulse (10–20 Hz) and projects the target waypoint forward by `Navigator.PathPrecision`. As the character runs, the calculated waypoint shifts by small fractions of a yard (0.1–0.4 yards).
- Because `0.05` sq yards (0.22 yards) is microscopically small, `DistanceSqr > 0.05` evaluated to `true` on **every single tick**, re-issuing `ClickToMoveType.Move` repeatedly.
- Re-issuing CTM to the WoW client at 10–20 Hz resets the game client's internal turning interpolation and camera heading damping, creating severe visual jitter and character shoulder twitching.

#### 3. Flightor Frame Skipping & Synchronous Freezes
- In `Styx.Pathing.Flightor.MoveTo`:
  - `int_0 % 2 == 0` discarded every alternate pulse (`brfalse.s ...; ret`), halving the effective responsiveness of the flight engine.
  - Waypoint navigation and takeoff contained multiple synchronous `StyxWoW.Sleep(100)` invocations (`IL_0a5f`, `IL_0c3c`, `IL_0c4d`) that blocked the primary bot thread, freezing the execution tree and causing hitching during flight.

#### 4. `Quest Behaviors\UseTransport.cs` Docking Radius
- Boarding and disembarking logic enforced `TransportLocation.DistanceSqr(Location) < 1.5 * 1.5` (1.5 yards = 4.5 feet).
- Because ships and zeppelins pitch, roll, and bob on water/air, or come to a halt slightly outside 1.5 yards of the nominal waypoint, the bot failed to detect docking, riding back and forth across continents indefinitely.

---

### 30.3 Remediation Applied

#### 1. Binary IL Patching via Mono.Cecil (`Honorbuddy.exe`)
- **`MeshNavigator.smethod_8` (Elevator SubType Filter)**:
  - Replaced the strict SubType check with an expanded check accepting both `Transport` (`11`) and `MapObjectTransport` (`15`):
    ```cil
    ldarg.0
    callvirt WoWGameObject::get_SubType()
    stloc V_0
    ldloc V_0
    ldc.i4.s 11
    beq.s IL_001a
    ldloc V_0
    ldc.i4.s 15
    bne.un.s IL_0038
    // Proceed to Entry blacklist checks
    ```
- **`MeshNavigator.method_10` (Elevator Z-Tolerances)**:
  - Broadened exit Z tolerance from `2.0f` to `4.0f`.
  - Broadened arrival/wait Z tolerance from `2.0f` to `4.5f`.
  - Ensures reliable boarding and disembarking on Orgrimmar, Thunder Bluff, and Undercity elevators without getting stuck at the edge.
- **`WoWMovement.ClickToMove` (Jitter Suppression)**:
  - Increased destination change threshold from `ldc.r8 0.05` (0.22 yards) to `ldc.r8 2.25` (1.5 yards squared).
  - While running along a path, minor micro-adjustments do not flood CTM commands into the WoW client, allowing the client's built-in movement smoothing to produce fluid, human-like straight-line running.
- **`Flightor.MoveTo` (Flight Engine Optimization)**:
  - Replaced `brfalse.s` with `Pop` and `ret` with `Nop` on the remainder calculation, allowing Flightor to pulse at full 100% frame rate without dropping frames.
  - Replaced 3 blocking `StyxWoW.Sleep(100)` thread stalls at `IL_0a5f`, `IL_0c3c`, and `IL_0c4d` with `Nop` instructions, eliminating flight stutter.

#### 2. `Quest Behaviors\UseTransport.cs` Overhaul
- Broadened transport arrival check from 1.5 yards 3D to 2D tolerance (`Distance2DSqr < 5.0 * 5.0`) with 3D fallback (`DistanceSqr < 6.0 * 6.0`).
- Broadened get-off waypoint arrival from `2.0 * 2.0` to `3.5 * 3.5`.
- Broadened waiting spot proximity check from `2.0 * 2.0` to `3.5 * 3.5`, preventing continuous micro-readjustments while waiting on transport docks.
